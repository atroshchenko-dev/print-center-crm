# Персональні дані: що зберігається і як довго

Політика зберігання персональних даних: без неї дані накопичувались би
рівно стільки, скільки живе база.

Цей файл — інвентар (що і де лежить) плюс політика (що і коли зникає).

---

|---|---|---|---|
| ПІБ підписанта | `order_approvals.signatory_name` | працівник університету | **знеособлюється через 365 днів** |

## 2. Політика: погодження

Реалізує `privacy:prune`, запускається планувальником щодня о **03:30**
(перед нічним бекапом о 04:00 — щоб дамп не консервував те, що вже мало зникнути).

**Строк:** `PRIVACY_APPROVAL_RETENTION_DAYS`, за замовчуванням **365 днів**.
Відлік від моменту, коли погодження перестало бути живим: від `responded_at`,
а для лінків, які ніхто так і не відкрив, — від `expires_at`.

**Що робить:** підміняє `signatory_name` і `signatory_email` на
`[видалено за політикою зберігання]`, обнуляє `responded_ip`, ставить
`anonymized_at`.

**Чого не робить:** не видаляє сам рядок. Факт «замовлення було погоджено,
тоді-то, з таким результатом» — це фінансовий контроль, він лишається назавжди.
Зникає лише можливість через рік знайти й ідентифікувати конкретну людину.

Команда ідемпотентна: `anonymized_at` позначає оброблене, повторний запуск
нічого не змінює. Кожен прогін пише в `audit_logs` подію `privacy_prune` —
тільки з кількістю, без жодного email.

```bash
php artisan privacy:prune --dry-run        # порахувати, нічого не міняти
php artisan privacy:prune --days=180       # разово інший строк
```

## 3. Свідомі винятки

**`audit_logs`** — таблиця append-only за ТЗ §6: і Eloquent-гарди, і
PostgreSQL-тригер `prevent_modification()` забороняють UPDATE та DELETE.
Чистити її означало б зламати саме той інваріант, заради якого вона існує.
Тому дані в `meta` лишаються. Якщо зберігання персональних даних у журналі
подій стане проблемою — правильна відповідь не «підчистити журнал», а
«перестати класти туди імена», тобто змінити те, що записується на вході.

**`order_items.material_description`** — ✅ **строк установлено 2026-07-31,
рішення власника**.

**365 днів, як для погоджень.** Відлік — від `orders.created_at`: саме тоді дані
зібрано, і для ретро-замовлення це не дата, коли робота виконувалась.
Знеособлення, не видалення: рядок, кількість і гроші лишаються, зникає лише
відповідь на питання «чиї це були візитівки».

**Тільки категорія «Візитівки».** Те саме поле в інших послугах містить зміст
замовлення — «Плакати», «Дипломи 2026, 3 курс» — і жодних персональних даних.
Затирати його означало б знищити історію без жодного виграшу для приватності.

**Мітка «вже оброблено» — сам плейсхолдер.** В `order_items` немає
`anonymized_at`, як в `order_approvals`, і додавати колонку заради нічного
прибирання означало б міграцію на живій таблиці. Рядки з плейсхолдером просто
не потрапляють у вибірку, тож повторний прогін — no-op.

**Пастка, записана свідомо:** правило прив'язане до **назви** категорії
(`ServiceCategory::BUSINESS_CARDS`), як і `ServiceParameterGroup::PAPER`. Якщо
категорію в адмінці перейменують, правило вимкнеться. Тому `privacy:prune`
друкує попередження, коли категорії з такою назвою немає, — щоб це впало гучно,
а не тихо зберігало дані назавжди.

```bash
php artisan privacy:prune --dry-run   # покаже і погодження, і рядки візитівок
```

## 4. Запит суб'єкта даних

Якщо працівник просить видалити свої дані:

```bash
# 1. Знайти всі його погодження
php artisan tinker
>>> App\Models\OrderApproval::withTrashed()->where('signatory_email', 'signer@example.edu')->get(['id','order_id','status','responded_at','anonymized_at']);

# 2. Знеособити достроково
>>> App\Models\OrderApproval::withTrashed()->where('signatory_email', 'signer@example.edu')->each->anonymize();
```

`anonymized_at` фіксує, коли саме дані було прибрано — це і є відповідь на
запит «коли ви це зробили».
